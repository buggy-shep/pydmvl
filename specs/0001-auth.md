# 0001 — Authentication

- **Status:** approved
- **Scope:** `pydmvl` authentication against the account API

## Summary

The account API authenticates every request with a login and a password hash
sent as request query parameters. There is no bearer token and no separate
session endpoint: the `authentication` action both authenticates the account
and returns the home-screen snapshot. This spec defines credential handling
and the authentication request.

## Motivation

Every read of account data requires valid credentials. The Home Assistant
integration needs a single, safe entry point that authenticates and returns the
account snapshot, without exposing credentials to consumers.

## Requirements

- R1 (MUST) The password is hashed with MD5 (hex digest, lowercase, UTF-8
  input) and sent as the `hash` query parameter. This is the observed wire
  format of the service.
- R2 (MUST) Credentials are held only in memory as `Credentials(login,
  password_hash)`; the library never stores or logs the plaintext password.
- R3 (MUST) `DmvlClient.login(login, password)` performs the `authentication`
  request, stores the credentials on success, and returns the parsed
  `Session`. Malformed credentials or a rejected login raise `AuthError`.
- R4 (MUST) `DmvlClient.fetch()` performs `authentication` with the stored
  credentials and returns a fresh `Session`; it raises `AuthError` when no
  credentials are stored.
- R5 (MUST) `DmvlClient.logout()` clears the stored credentials.
- R6 (MUST) Requests send no `Authorization` header; the credentials travel in
  query parameters. The library must not log request URLs, credentials, or the
  password hash.
- R7 (MUST) A non-200 HTTP response raises `ApiError` carrying the status; a
  non-JSON body raises `ApiError`; an error payload (`error` truthy) raises
  `AuthError` for the authentication action.
- R8 (SHOULD) An optional `version` query parameter may be configured (the
  service observes an application version); requests set `Accept:
  application/json` and use a configurable timeout (default 30 seconds).

## Design

- One httpx client per `DmvlClient`; the base URL and transport are
  overridable for tests (`httpx.MockTransport`).
- The `authentication` action is a `GET` to `api.php` with `action=login`,
  `hash`, and optional `version`. The response is the whole home screen, parsed
  by spec 0002 (documents) and spec 0003 (payments).

## API

```python
@dataclass(frozen=True)
class Credentials:
    login: str
    password_hash: str

    @classmethod
    def from_password(cls, login: str, password: str) -> Credentials: ...


def password_hash(password: str) -> str: ...


class DmvlClient:
    def __init__(
        self,
        *,
        base_url: str = "https://houseb.ru/api/",
        version: str | None = None,
        transport: httpx.BaseTransport | None = None,
        timeout: float = 30.0,
    ) -> None: ...
    def login(self, login: str, password: str) -> Session: ...
    def fetch(self) -> Session: ...
    def logout(self) -> None: ...
    def close(self) -> None: ...
```

(Async variants are defined in spec 0004.)

## Test plan

- httpx MockTransport fixtures: successful `authentication`; error payload;
  non-200 status; malformed body.
- Assert the request carries `action`, `login`, `hash`, and no `Authorization`
  header; assert `hash` equals the MD5 of the password.
- Assert the password hash is never emitted through the library logger.
- `fetch()` without login raises `AuthError`; `logout()` clears credentials.

## Acceptance criteria

- Unit tests green (mock transport); gate green; skeptic without `BLOCKING`.
- Live (manual, `live` marker): login with real credentials from
  `DMVL_USERNAME`/`DMVL_PASSWORD` succeeds.

## Out of scope

- Password recovery, access-code login, and account linking actions.
- Access/refresh tokens (the service is stateless for this API).
- Writing actions of any kind.

`approved` (2026-10-01: gate for the 0.1.0 scope).
